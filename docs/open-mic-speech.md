# FareSniper 产品开放麦演讲稿

总时长：约 14 分 40 秒，预留 20 秒处理翻页、停顿或现场数据延迟。

核心句：**特价不是一个统一的最低数字，而是满足个人约束之后，仍然值得购买的相对最优解。**

## 第 1 页：开场（0:00—0:30）

大家好，我今天带来的产品叫 FareSniper。

现在搜索一张机票其实并不困难，困难的是搜完以后，我们还是不知道这张票到底该不该买。因为真正的“特价”，对每个人都不一样。

所以 FareSniper 惟一想做好的事情是：记住你如何定义特价，再用多平台证据帮你做一次可信的机票决策。

转场：在介绍产品之前，我先用两分半钟介绍一下，我为什么会做这个方向。

## 第 2 页：关于我（0:30—3:00）

大家好，我叫陈永琪，目前在中国科学院大学读信息系统工程管理硕士，主要关注 AI Agent 和复杂 AI 平台的产品落地。

我过去几段经历，刚好构成了 FareSniper 的三个技术支点。

第一段是在 Keep 的 AI 平台事业部。当时我参与过从 Workflow 向 Agent 模式的升级。它让我第一次真正意识到，一个 Agent 并不是接上大模型、再配一个聊天框。它需要状态管理，需要知道什么时候调用工具，需要处理多轮对话，也需要在关键结果上做确定性校验。

第二段是在智谱 Z.ai。我做过多模态模型评测和 Bad Case 闭环。我们把一道题是否判对拆成可重复的评测规则，再根据错误类型持续修正数据和流程，最终把规则一致率提升到了 98.5%。这段经历让我形成了一个习惯：不能只看 Demo 看起来聪明，而要追问结果能不能被验证，错误能不能被定位。

第三段是在百度百舸 AIHC。我接触的是资源池、队列权限和调度策略这类复杂平台问题。它让我理解，一个 AI 产品要稳定运行，背后一定需要清晰的资源边界、失败处理和工程约束。

FareSniper 就是这三段经历的交汇点：前面是自然语言交互，中间是 Agent 和工具编排，后面是可验证的数据、评测与工程系统。

转场：但我做它最直接的原因，来自一个非常日常的问题——我们口中的“特价”，其实根本不是同一个东西。

## 第 3 页：用户洞察（3:00—4:10）

用户真正焦虑的，不是找不到机票，而是价格一直在变。

同一条航线，早上可能是 620 元，下午变成 480 元，晚上又回到 560 元。一次搜索只能截到其中一个点，却不能回答最重要的问题：我现在到底该不该买？

这个问题落到三类人身上，又是三个不同答案。刚需用户固定周五晚上出发，他等的是价格进入自己的心理区间；弹性用户可以换日期，他等的是某一天出现低点；带行李用户等的不是裸价下降，而是加上机建燃油和行李后仍然划算。

所以 FareSniper 监控的不是一个统一最低价，而是每个用户自己的购买窗口：出行约束满足、完整成本可接受、当前价格进入个人阈值。

转场：但市场上已经有比价、提醒和 AI，为什么这个问题还没有被完整解决？

## 第 4 页：竞品与市场缺口（4:10—5:10）

我不做一张品牌功能表，只问三个用户问题。

第一个问题是“现在谁便宜”。OTA 和比价产品很擅长回答此刻有哪些票，但跨平台的税费、行李和数据口径仍然需要用户自己核对。FareSniper 的竞争力是把多来源报价统一成同一份可比较事实。

第二个问题是“什么时候买”。Google Flights、Skyscanner 和 Hopper 都证明了价格追踪与提醒有真实需求，但价格曲线通常没有和一个人的固定时段、预算、行李及历史选择放进同一次判断。FareSniper 监控的是个人购买窗口，而不只是价格涨跌。

第三个问题是“哪张适合我”。通用 AI 能理解自然语言，却未必拥有持续、可追溯的交易级价格事实。FareSniper 让记忆参与排序，同时让结论绑定来源、数据新鲜度和完整成本。

所以市场不是没有单点能力，而是动态价格、完整成本和个人约束还没有形成一条可信链路。

转场：FareSniper 的产品创新，就是把这三件事接成持续决策闭环。

## 第 5 页：产品方案（5:10—6:30）

整个闭环有四步。

第一步，定义购买条件。用户说出航线、日期、预算、时段和行李；缺少真正影响搜索的要素就先追问。

第二步，实时拉取。用户搜索时，系统并发获取当前可用报价，先返回已经完成的来源，不让一个慢平台拖住全部结果。

第三步，持续监控。用户关注航线后，系统继续刷新价格并记录快照、新鲜度和平台状态。Search 回答“现在有什么”，Monitor 回答“什么时候值得买”。

第四步，解释并提醒。当价格进入个人阈值，系统结合完整成本和长期记忆给出建议；回答、卡片和提醒都引用同一份事实。

所以创新点不是增加一个聊天框，而是把一次查询变成一段持续到购买窗口出现的决策关系。

转场：下面我用一句真实的自然语言演示这个过程。

## 第 6 页：现场演示（6:30—9:00）

演示输入：**“下周五从北京到长治。”**

第一步，大家可以看到，系统不会直接把“下周五”交给模型随意理解，而是结合当前日期转换成明确的年月日。城市也会映射到实际机场查询范围，避免只认三字码、漏掉同城机场。

第二步，前端保持“正在为你搜寻”的产品状态，Agent 在后台选择航班搜索工具，并并行读取不同来源。

第三步，结果进入统一的数据结构。无论原始数据来自飞猪、携程还是国际平台，最终都会变成同一种 FlightOffer，包含航班、出发时间、票价、税费、行李、平台名称、跳转链接和数据新鲜度。

第四步是推荐。这里不是让大模型重新阅读网页并编一个结论，而是先由确定性代码计算可比较总价、过滤不满足条件的结果，再把候选事实交给模型解释。

大家可以看到，卡片会明确展示 250 元票价、100 元机建燃油、20KG 行李额，以及不同平台的价格。对话中的价格也必须引用这张卡使用的同一份结构化结果，所以不会再出现 AI 说 700 元、卡片却显示 650 元的情况。

最后，如果用户点击、收藏或设置盯价，这次行为会成为新的偏好信号。下一次系统排序时，会更接近这个用户自己的“特价”标准。

演示收束：这不是让 AI 替用户做一个不可解释的决定，而是让它把证据整理好，再代表用户进行判断。

### Demo 网络异常时的兜底话术

现场网络如果没有及时返回，就停留在演示页的价格卡，不要重复刷新：

“现场数据源还在返回，我先用这张相同结构的结果卡说明。产品会诚实保留‘正在获取’或‘暂时不可用’状态，而不会为了完成回答伪造价格。这也是我把供应商状态做成产品能力的一部分，而不是简单报错的原因。”

## 第 7 页：完整系统架构（9:00—11:00）

这张图按职责把 FareSniper 拆成五层，而不是把所有逻辑塞进一个 Agent。

A 是交互与上下文层。Next.js 负责输入和 SSE 展示，FastAPI 完成鉴权与 request scope；Redis 保存短期会话，PostgreSQL 保存长期偏好和行为，模型不会自己猜历史。

B 是意图与编排层。Intent Registry 先召回候选，确定性代码抽取机场、日期、预算和行李，再校验必填槽位；只有歧义部分交给 ReAct。LangGraph 选择 Typed Tool，用户身份和 Provider 凭证由 Tool Router 注入，所以模型不能越权直连数据源。

C 是数据执行层。Aggregator 通过统一 FlightProvider Contract 并发调用 FlyAI、携程快照和 SerpAPI。每个来源独立超时和熔断，`as_completed` 让可用结果先返回，慢来源不会拖垮整次请求。

D 是事实与决策层。所有结果归一为 FlightOffer，保留来源、新鲜度和 null；Truth Engine 再做报价资格、完整成本和排序，最后冻结为 ResponseFacts。FlightOffer 约束输入事实，ResponseFacts 约束所有输出。

E 是交付与反馈层。SSE、AI 文案和价格卡片都读取 ResponseFacts；PriceAlert 和 Worker 复用同一价格口径。用户点击、盯价和购买信号再写回 PostgreSQL，进入下一次 Context Bootstrap。

横向 Harness 贯穿五层，统一承担 Auth、State、Schema、Timeout、Grounding 和 Idempotency；LangSmith 与契约测试提供证据。模型只负责理解歧义、规划工具和解释结果。

转场：当前架构已经能运行，下一步工程重点不是继续堆功能，而是补齐可靠性和扩展性。

## 第 8 页：工程能力演进（11:00—12:30）

上方是监控链路。前三个绿色节点已经实现：PriceAlert、15 分钟 Scheduler 和数据刷新；后面三个是下一阶段：PurchaseWindowEvaluator、事务 Outbox 和多渠道通知。

下面四项是我按风险排出的工程优先级。

P1 是调度与扩展。当前单 Worker 固定轮询，下一步根据出发日期和接近目标价的程度做自适应频率，并加入优先级队列和分布式锁。

P2 是事件可靠性。当前触发后直接 Web Push，下一步采用 Transactional Outbox、幂等键、重试与 DLQ，保证通知不丢、不重，也能审计。

P3 是数据质量。在已有 status、freshness 和 null 保真的基础上，增加来源 SLO、Schema Version、Provenance 和 Fixture Replay，让异常报价可以离线重放。

P4 是发布治理。在 LangSmith 和自动化测试之上，补齐业务与系统 SLO、Feature Flag、Canary 和一键回滚。

购买窗口仍由确定性公式触发；大模型只解释 reason codes，不改变触发条件。这样扩容、换模型或增加微信与飞书渠道，都不会改变业务正确性。

转场：链路能运行还不够，我还要证明错误能够被发现、复现，并且不再回来。

## 第 9 页：评测与 Bad Case 闭环（12:30—14:10）

我的评测分成离线和在线两条线。

离线已经有 50 条种子样本：25 条正常主路径、8 条相对日期、8 条多轮追问、6 条边界异常，以及 3 条 Prompt Injection 和密钥套取等对抗样本。B 类 runner 从意图准确、追问准确、信号准确、建议相关性和格式合规五个维度生成报告。这里我不展示未经稳定复跑的漂亮数字，先展示评测结构和门禁方式。

在线由 LangSmith 记录 flight search、provider、normalize、rank 和 stream results 等 span，并对敏感字段脱敏。出现问题后，先根据影响范围分成 P0 到 P3，再保存最小输入、会话状态和 Provider fixture，判断它属于模型、状态、工具、数据源、排序还是输出层。修复后必须补单元、契约或 E2E 回归测试，才能重新部署。

页面右侧是四类真实 Bad Case。第一类是用户修改航线后错误沿用旧日期，修复方式是清空旧日期并重新校验必填槽位。第二类是慢 Provider 拖垮整个请求，现在通过并发隔离、超时、熔断和部分结果测试处理。第三类是不符合资格或币种不一致的报价错误成为最低价，现在由携程快照契约、winner 资格和币种原子性约束。第四类是 AI 说 700 元、卡片显示 650 元，或者把未知行李当免费，现在统一由 ResponseFacts 和 null 保真解决。

所以 Bad Case 对我不是事故记录，而是 Harness 的回归资产。每发现一个新错误，系统能够确定兜住的边界就扩大一点。

转场：最后，我想用一句话说明 FareSniper 想走向哪里。

## 第 10 页：结尾（14:10—15:00）

FareSniper 目前仍然有明确边界。部分平台不会稳定返回完整税费和行李字段，携程实时采集也会受到网络与反爬限制。所以现阶段最重要的原则不是假装什么都有，而是诚实展示数据状态，并持续增加合规数据源。

下一步我会继续做三件事：扩大国内外航线的数据覆盖，把一次搜索升级为持续价格监控，以及让记忆真正参与可解释排序。

FareSniper 不想成为另一个卖票平台。它更希望站在用户这一边，记住用户真正关心的东西，用多平台证据验证价格，在合适的时候给出一条能够解释、也能够追溯的购买建议。

最后一句：**懂你的标准，才叫真特价。谢谢大家。**

## 可能的现场提问

### 1. 你和传统比价网站有什么区别？

传统比价主要解决“同一次查询中哪里更便宜”，FareSniper 还会结合时间、行李、预算和长期偏好，解释为什么这张票更适合这个用户，并支持后续持续监控。

### 2. 价格数据不完整时，推荐还可信吗？

不完整字段不会被模型补全。系统会降低结果的可比较等级，明确标注待确认，并把用户引导到预订页核验；只有满足新鲜度和字段条件的结果才参与实时最低价判断。

### 3. 为什么需要大模型？规则系统不够吗？

规则适合日期、价格与排序，但不擅长处理自然语言里的省略、上下文和偏好表达。大模型负责理解和编排，确定性系统负责事实和计算，二者职责不同。

### 4. 记忆会不会造成新的“杀熟”？

记忆只影响排序、提醒和解释，不修改供应商价格。用户可以查看和修改记忆，推荐依据也应该可解释。

### 5. 数据源是目前最大的风险吗？

是。当前阶段最重要的不是无限扩平台，而是优先接入合规、稳定、能提供完整字段的数据源，同时把超时、过期和缺失做成可见状态。

### 6. 如何衡量这个 Agent 是否有效？

除了搜索成功率，还要看关键要素追问准确率、价格与卡片一致率、完整成本覆盖率、有效跳转率、设置盯价率，以及用户完成一次购买决策所需时间。

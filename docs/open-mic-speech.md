# FareSniper 产品开放麦演讲稿

总时长：约 14 分 30 秒，预留 30 秒处理翻页、停顿或现场数据延迟。

核心句：**特价不是一个统一的最低数字，而是满足个人约束之后，仍然值得购买的相对最优解。**

## 第 1 页：开场（0:00—0:30）

大家好，我今天带来的产品叫 FareSniper。

现在搜索一张机票其实并不困难，困难的是搜完以后，我们还是不知道这张票到底该不该买。因为真正的“特价”，对每个人都不一样。

所以 FareSniper 惟一想做好的事情是：记住你如何定义特价，再用多平台证据帮你做一次可信的机票决策。

转场：在介绍产品之前，我先用两分半钟介绍一下，我为什么会做这个方向。

## 第 2 页：关于我（0:30—3:00）

大家好，我叫陈永琪，目前在中国科学院大学读信息系统工程管理硕士，主要关注 AI Agent 和复杂 AI 平台的产品落地。

我过去几段经历，刚好构成了 FareSniper 的三个技术支点。

第一段是在 Keep 的 AI 平台事业部。当时我参与过从 Workflow 向 Agent 模式的升级。它让我第一次真正意识到，一个 Agent 并不是接上大模型、再配一个聊天框。它需要状态管理，需要知道什么时候调用工具，需要处理多轮对话，也需要在关键结果上做确定性校验。

第二段是在智谱 Z.ai。我做过多模态模型评测和 Bad Case 闭环。我们把一道题是否判对拆成可重复的评测规则，再根据错误类型持续修正数据和流程，最终把规则一致率提升到了 98.5%。这段经历让我形成了一个习惯：不能只看 Demo 看起来聪明，而要追问结果能不能被验证，错误能不能被定位。

第三段是在百度百舸 AIHC。我接触的是资源池、队列权限和调度策略这类复杂平台问题。它让我理解，一个 AI 产品要稳定运行，背后一定需要清晰的资源边界、失败处理和工程约束。

FareSniper 就是这三段经历的交汇点：前面是自然语言交互，中间是 Agent 和工具编排，后面是可验证的数据、评测与工程系统。

转场：但我做它最直接的原因，来自一个非常日常的问题——我们口中的“特价”，其实根本不是同一个东西。

## 第 3 页：核心洞察（3:00—4:10）

比如同样是北京到上海。

有人第二天早上必须参加会议，他只能选择周五晚上出发。对他来说，时间匹配比便宜一百块更重要。

也有人时间非常灵活，只要足够便宜，周二或者周三出发都可以。

还有人带着 20 公斤行李。平台上看起来最便宜的裸票价，加上托运行李之后，可能反而最贵。

所以“特价”不应该被定义成一个全网统一的最低数字。它应该是：满足出行约束，加上机建燃油、行李和时间成本之后，仍然符合个人偏好的相对最优解。

转场：当我们需要自己去多个平台验证这些信息时，第二个问题就出现了——信任。

## 第 4 页：信任缺口（4:10—5:10）

现在的推荐系统通常只给我们一个答案，却很少给出足够的证据。

我不需要先证明某个平台一定存在“杀熟”，但用户确实很难验证：这个结果究竟是最适合我的，还是平台最希望我购买的。

右边这个例子里，平台 A 裸价最低，但税费未知；平台 C 看起来只有 399 元，加上税费和行李之后却变成 619 元；真正完整成本最低的是平台 B。

所以 FareSniper 不只展示一个推荐答案。它会保留来源、数据新鲜度、票价、税费和行李信息。平台没有返回的字段就明确写“待确认”，而不是让模型补一个看起来合理的数字。

转场：基于这两个问题，我把产品设计成了一个持续决策闭环。

## 第 5 页：产品方案（5:10—6:30）

整个闭环有四步。

第一步是理解。用户可以直接说“下周五从北京到长治”，系统提取城市、日期、预算、时间偏好和行李约束；如果缺少影响搜索的关键要素，就先追问确认。

第二步是比较。不同平台的数据通过统一 Provider 接入，目前国内主要使用飞猪实时结果和携程价格快照，国际航线可以接入 Google Flights 等来源。

第三步是解释。结果不会只剩一个最低价，而会拆出票价、机建燃油、行李额、平台来源和数据状态，并保证 AI 对话里说的价格与卡片来自同一份结构化数据。

第四步是记住。系统会区分一次会话里的临时需求和长期偏好，例如用户经常选择直飞、对红眼航班敏感，或者愿意为免费行李多付多少钱。

这样它就从一次性的搜索工具，变成一个越来越理解用户标准的决策 Agent。

转场：下面我用一句真实的自然语言演示这个过程。

## 第 6 页：现场演示（6:30—9:00）

演示输入：**“下周五从北京到长治。”**

第一步，大家可以看到，系统不会直接把“下周五”交给模型随意理解，而是结合当前日期转换成明确的年月日。城市也会映射到实际机场查询范围，避免只认三字码、漏掉同城机场。

第二步，前端保持“正在为你搜寻”的产品状态，Agent 在后台选择航班搜索工具，并并行读取不同来源。

第三步，结果进入统一的数据结构。无论原始数据来自飞猪、携程还是国际平台，最终都会变成同一种 FlightOffer，包含航班、出发时间、票价、税费、行李、平台名称、跳转链接和数据新鲜度。

第四步是推荐。这里不是让大模型重新阅读网页并编一个结论，而是先由确定性代码计算可比较总价、过滤不满足条件的结果，再把候选事实交给模型解释。

大家可以看到，卡片会明确展示 250 元票价、100 元机建燃油、20KG 行李额，以及不同平台的价格。对话中的价格也必须引用这张卡使用的同一份结构化结果，所以不会再出现 AI 说 700 元、卡片却显示 650 元的情况。

最后，如果用户点击、收藏或设置盯价，这次行为会成为新的偏好信号。下一次系统排序时，会更接近这个用户自己的“特价”标准。

演示收束：这不是让 AI 替用户做一个不可解释的决定，而是让它把证据整理好，再代表用户进行判断。

### Demo 网络异常时的兜底话术

现场网络如果没有及时返回，就停留在演示页的价格卡，不要重复刷新：

“现场数据源还在返回，我先用这张相同结构的结果卡说明。产品会诚实保留‘正在获取’或‘暂时不可用’状态，而不会为了完成回答伪造价格。这也是我把供应商状态做成产品能力的一部分，而不是简单报错的原因。”

## 第 7 页：意图识别的分层路由（9:00—11:20）

这一页我重点回答一个问题：用户只说一句“下周五从北京到长治”，系统到底怎么知道他想做什么？

我的实现不是把整句话交给大模型做一次分类，而是分成四层。

第一层是候选召回。意图不是写死在一个 Prompt 里，而是以 Intent Definition 的形式放在 PostgreSQL，里面包含关键词、正反例、必填槽位和处理器；运行时缓存到 Redis，TTL 是 60 秒。规则层先用关键词、示例和模糊匹配召回候选。这样新增或调整意图不需要重新发布整套 Agent。

第二层是可选快速路径。如果模型供应商支持 Embedding，系统会把用户表达与意图示例做近邻匹配，生成一个 fast hint。但这个 hint 只是加速，不是最终答案。当前 DeepSeek 路径没有可用的 Embedding 接口，系统会自动跳过，回到关键词和语义路由。也就是说，优化能力可以插拔，但正确性不能依赖它。

第三层是 ReAct 语义路由。Agent 同时读取当前北京时间、Redis 中的会话槽位、PostgreSQL 中的长期偏好、动态意图定义以及刚才的 hint，再决定应该追问、搜索航班、读取偏好还是设置提醒。这里大模型最有价值的能力是理解省略和歧义，并规划下一步工具，而不是直接生成搜索事实。

第四层是确定性抽槽和状态校验。机场由 AirportCatalog 识别，相对日期、预算和直飞等约束由代码解析，再和上一轮状态合并。搜索必须同时具备出发地、目的地和出发日期；缺少就先追问。用户改了航线却没有重新说日期时，旧日期会被清空，避免把上一条行程的时间错误沿用。会话里的 sticky intent 保持多轮连续性，但置信度不低于 0.90 的强新意图可以打断它。

ReAct 单次调用有 8 秒上限。超时或模型失败后，LangGraph 会进入 deterministic fallback，继续用确定性槽位链追问或搜索。所以这里体现的不是“模型识别得多准”，而是 Harness 如何让识别过程可配置、可回退、可校验。

转场：意图识别只是 Harness 的一部分。下一页我把模型周围这套工程系统完整展开。

## 第 8 页：Harness 工程（11:20—13:20）

我理解的 Harness Engineering，是围绕一个概率模型，建立一套确定、可观测、可恢复的任务执行环境。模型可以替换，但系统的正确性边界不能跟着漂移。

第一层是 Context Harness。Redis 保存 30 分钟会话状态，PostgreSQL 保存长期偏好，动态 Intent Registry 提供当前可用能力。进入模型的上下文由系统组装，不靠模型自己回忆。

第二层是 State 与 Policy Harness。LangGraph 把 bootstrap、ReAct、tool router 和 render response 组织成状态机；槽位如何合并、什么时候追问、什么时候进入 fallback，都有明确策略，而不是让模型自由发挥。

第三层是 Tool 与 Data Harness。工具参数有类型约束，用户 ID 由服务端注入，模型不能伪造身份。航班搜索通过统一 Provider Contract 接入飞猪实时、携程快照和国际来源；每个 Provider 有 10 秒超时，连续失败三次触发熔断，30 秒后再试探恢复。前端会逐步收到 started、provider status 和 results，所以单一数据源失败不会拖垮整个请求。

第四层是 Truth Harness。所有报价归一化为 FlightOffer，缺失税费和行李保留 null。只有满足新鲜度、金额和可追溯链接条件的报价，才有资格成为 winner。最终结果深拷贝并冻结为 ResponseFacts，对话文案和前端卡片只读取这一份事实，解决 AI 说 700 元、卡片显示 650 元的问题。

第五层是 Evaluation Harness。LangSmith 记录 flight_search、provider、normalize、rank 和 stream results 等 span，并在输入中做敏感字段脱敏。线上 Trace 进入 Bad Case，问题被定位到模型、规则、Provider 或映射层；修复后补回归测试，再观察下一批 Trace。

所以我对模型和 Harness 的分工很明确：模型负责理解歧义、规划工具和生成解释；Harness 负责 Context、State、Tools、Guardrails、Truth 和 Evaluation。不是把模型做得更大，而是把它周围的 Harness 做完整。这样即使切换模型、Embedding 不可用，或者某个 Provider 失败，Agent 仍然能保持可解释的退化路径。

转场：最后，我想用一句话说明 FareSniper 想走向哪里。

## 第 9 页：结尾（13:20—14:30）

FareSniper 目前仍然有明确边界。部分平台不会稳定返回完整税费和行李字段，携程实时采集也会受到网络与反爬限制。所以现阶段最重要的原则不是假装什么都有，而是诚实展示数据状态，并持续增加合规数据源。

下一步我会继续做三件事：扩大国内外航线的数据覆盖，把一次搜索升级为持续价格监控，以及让记忆真正参与可解释排序。

FareSniper 不想成为另一个卖票平台。它更希望站在用户这一边，记住用户真正关心的东西，用多平台证据验证价格，在合适的时候给出一条能够解释、也能够追溯的购买建议。

最后一句：**懂你的标准，才叫真特价。谢谢大家。**

## 可能的现场提问

### 1. 你和传统比价网站有什么区别？

传统比价主要解决“同一次查询中哪里更便宜”，FareSniper 还会结合时间、行李、预算和长期偏好，解释为什么这张票更适合这个用户，并支持后续持续监控。

### 2. 价格数据不完整时，推荐还可信吗？

不完整字段不会被模型补全。系统会降低结果的可比较等级，明确标注待确认，并把用户引导到预订页核验；只有满足新鲜度和字段条件的结果才参与实时最低价判断。

### 3. 为什么需要大模型？规则系统不够吗？

规则适合日期、价格与排序，但不擅长处理自然语言里的省略、上下文和偏好表达。大模型负责理解和编排，确定性系统负责事实和计算，二者职责不同。

### 4. 记忆会不会造成新的“杀熟”？

记忆只影响排序、提醒和解释，不修改供应商价格。用户可以查看和修改记忆，推荐依据也应该可解释。

### 5. 数据源是目前最大的风险吗？

是。当前阶段最重要的不是无限扩平台，而是优先接入合规、稳定、能提供完整字段的数据源，同时把超时、过期和缺失做成可见状态。

### 6. 如何衡量这个 Agent 是否有效？

除了搜索成功率，还要看关键要素追问准确率、价格与卡片一致率、完整成本覆盖率、有效跳转率、设置盯价率，以及用户完成一次购买决策所需时间。
